## 1. 왜 필요한가

현재 게임은 마법·완성 합성·유물을 처음 발견하면 **영구 프로필에 ID를 보관**한다. 하지만 플레이어는 그 행동이 **처음 해낸 업적**이라는 피드백을 거의 느끼지 못한다.

플레이어 질문:
1. 이번에 획득한 구체가 **이미 알고 있던 마법**인가, **영구적으로 처음 발견한 마법**인가?
2. 첫 완성 합성이 왜 일반 마법 획득보다 특별한가?
3. 작은 알림을 놓쳐도 나중에 도감에서 새 항목을 볼 수 있는가?
4. 전투 중 경고·보상·획득 안내·스토리 대사와 새 발견이 겹쳐 플레이를 방해하지 않는가?

**추천 결론:**
- **기본 마법/유물 첫 발견:** 작은 비정지형 발견 카드.
- **완성 합성 첫 발견:** 같은 카드 문법을 사용하되 더 큰 아이콘과 짧은 반짝임·강조.
- **이미 발견했던 마법 재획득·+1~+3 강화:** 별도 `처음 발견` 알림 없음. 기존 획득/강화 연출은 유지.
- **발견 도감:** 선택한 적 없는 신규 항목에 `NEW` 표시를 남기는 기능은 별도 저장 상태 확장이 필요한 **제안**이다.
- **획득이 확정된 이후**만 알림을 발생시키며 확인 버튼으로 전투를 추가 정지시키지 않는 방안을 우선.

### 3.1 현재 영구 발견 구조

`PlayerProfile.data`:
- `discovered_spells: []`: 일반 기본 마법 **기본 ID**.
- `discovered_fusions: []`: 완성 합성 마법 **기본 ID**.
- `discovered_relics: []`: 유물 **ID**.
- 이 기록은 `user://profile-v1.json`에 저장하며, **현재 런이 종료되거나 다음 실험을 시작해도 유지**한다.
- `profile.discover(parts, relic_ids)`는 새로 추가된 항목이 **하나라도 있는지 bool**로 반환할 뿐, **이번에 추가된 항목의 ID 목록을 직접 반환하지 않는다**.
- 일반 주문은 `Spells.Progression.base_id()`를 사용하므로 이미 발견한 기본 주문의 **강화 +1/+2/+3은 새 종류 발견이 아니다**.
- 일반 주문/합성/유물별로 판정 배열이 분리되어 있어 서로 다른 신규 종류를 알 수 있는 근거는 있다.

`game.discover_owned()`는 `profile.discover(economy.inventory.keys(), relics.owned)`를 호출하고 변경 시 프로필 저장을 시도한다. 호출 지점은 **시작 런, 체크포인트 저장/복원, 상점 구매, 제작·합성, 유물 획득, 전투 보상 완료** 등이다. 전투 보상 `finish_award()`도 발견을 기록한다.

**기본 주의:** 단순 `이번 런에 없는 아이템`과 `프로필에 영구적으로 한 번도 발견한 적 없는 아이템`은 완전히 다른 조건이다. 현재 보상 모델에 있는 `새 마법` 문구를 영구 첫 발견의 근거로 직접 사용해서는 안 된다.

### 3.2 일반 획득 연출과 겹칠 수 있는 현행 UI

- `game.announce(message, duration)`: `notice`/ `notice_left` **단일 문자열 통로**. 후속 메시지가 앞 메시지를 덮을 수 있다.
- `reward_reveal.gd::receipt()`: 일반 마법의 `OO 획득!` 같은 별도 수령 메시지와 애니메이션(표시 약 2.4초 이후 페이드).
- `acquisition_view.gd`: 레벨·상자·제작·오브 보상 정보 모델. `새`, `강화`, `완성 합성`, `새 유물` 등의 **현재 획득 맥락** 표시.
- `game.acquire_relic()`: 유물 획득 뒤 `discover_owned()` 호출 및 `유물 완성 · 이름` 공용 `announce()`.
- `combat_rewards.gd`: 상자 보상은 다중 결과를 연달아 지급할 수 있으며 `last_chest_results` 기록, 이미 별도의 보상 선택/편집 단계 정지 정책이 있음.

**문제 가설:** 신규 발견 전용 토스트를 추가하면서 현재 `announce()`와 보상 영수증을 그대로 사용하면 **같은 아이템의 중복 축하**, **순간적인 메시지 덮어쓰기**, 여러 건 동시 해금 시 마지막 항목만 보이는 상황이 발생할 수 있다. 이는 구현 전 예상 위험이며 아직 재현 테스트는 하지 않았다.

### 3.3 복원/이관·훈련장 경계

- `PlayerProfile.load_profile()`는 최근 기록을 훑어 과거 런의 조합·유물을 추가로 발견 처리할 수 있다. **구버전 기록 이관은 새로 얻은 행동이 아니다.**
- 체크포인트 복원 뒤 `discover_owned()`가 다시 호출된다. **이미 저장된 항목을 재발견했다고 축하하면 안 된다.**
- `game.discover_owned()`는 `checkpoint_loading` 또는 `meter != null`에서 조기 반환한다. **훈련/측정 모드에서 우발적으로 영구 도감을 기록하거나 발견 알림을 띄우지 말아야 한다.**
- `save_profile()`의 실패 가능성은 기존 코드에 존재. UI의 `영구 기록 완료` 문구는 실제 저장 실패를 완전한 성공으로 포장하지 않아야 한다.
- 새 게임에서 시작 마법 여러 종류를 동시에 얻을 수 있으나, **한꺼번에 모두 화면을 점거하는 축하 연출은 피한다.**

## 4. 제안하는 발견 알림 세 등급

### A. 기본 주문 첫 발견 — 작은 토스트

```text
┌──────────────────────────────────┐
│ [아이콘]  새로운 마법 발견!       │
│          별빛탄                  │
│          도감에 기록되었어!      │
└──────────────────────────────────┘
```

- 전투 비정지, 작은 폭·높이, 간결한 아이콘/제목/한 줄 설명.
- 기본 마법 역할(공격/보조/연결)을 작게 표시하는 안은 가능하지만 필수 아님.
- **추천 시안 길이:** 약 **1.5~2초** 내 등장·유지·퇴장. 실측 검증 전의 제안값.
- 키보드/콘트롤러 사용자도 볼 수 있는 표시 시간·가독성 검토.
- 기본 주문을 한 번에 여러 개 발견하면 **묶음 표시 또는 짧은 큐**로 전장 방해 최소화.

### B. 완성 합성 첫 발견 — 특별한 카드

```text
      ✦ 새로운 완성 합성 발견! ✦
             [큰 아이콘]
            합성 마법 이름
       새로운 주문이 도감에 기록!
```

- **한 판에서 +3 재료 두 종류로 처음 완성한 합성**의 특별함을 시각적으로 구분.
- Magicraft/Slay the Spire의 강조를 참고하되, **긴 전체 화면 컷신 대신 원래 합성/보상 화면의 요소를 우선 활용**.
- 큰 아이콘, 짧은 반짝임/입자, 상대적으로 뚜렷한 효과음 **한 번**(기존 SFX 설정 존중).
- **추천 시안 길이:** 보상 연출 안에서 **1.5~2.5초**, 사용자 미관 검증 전 확정 아님.
- 합성은 여러 종류가 있을 수 있다. 한 번의 상자에서 여러 신규 합성이 나오면 **각각의 이름을 보장하되 긴 연출이 무한 누적되지 않도록** 큐·묶음 처리.
- 같은 합성 재획득/재확인은 특별 발견 연출을 반복하지 않는다.

### C. 유물 첫 발견 — 기본 마법과 같은 짧은 카드

```text
┌──────────────────────────────────┐
│ [유물 아이콘]  새로운 유물 발견! │
│               금이 간 왕관       │
│               도감에 기록되었어! │
└──────────────────────────────────┘
```

- 카드 크기/행동은 기본 마법과 통일하되 **유물 전용 색상과 아이콘**으로 구별.
- 실제 유물 획득 완료 뒤에만 알림. 유물 후보 3개를 미리 보는 동안 발견으로 취급하지 않는다.
- 보상 선택 화면/제작 화면에서 이미 유물 카드가 크게 보일 경우 **해당 카드에 '첫 발견' 강조를 결합하거나 화면 밖 작은 토스트**로 중복 최소화.

### 4.1 분류별 표시 규칙

| 실제 상황 | 영구 첫 발견으로 알릴까? | 기본 권장 표시 |
|---|---|---|
| 시작 조합의 마법이 프로필에 처음 기록됨 | **예**, 시작 연출과 동시 중첩 금지 | 첫 시작 시 묶음/지연 |
| 레벨업으로 처음 획득한 기본 마법 | **예** | 작은 마법 토스트 |
| 이전 실험에서 발견한 기본 주문의 이번 런 첫 보유 | **아니오** | 기존 획득 안내만 |
| 기본 주문 +1/+2/+3 강화 | **아니오** | 강화 피드백만 |
| 특정 완성 합성을 영구 프로필에 처음 기록함 | **예** | 강화된 합성 발견 연출 |
| 이미 알고 있는 완성 합성 재획득 | **아니오** | 합성 완료 안내만 |
| 실제 처음 획득한 유물 | **예** | 작은 유물 토스트 |
| 이미 발견된 유물의 다른 런 재획득 | **아니오** | 기존 유물 획득 안내만 |
| 상점/보상 후보 미리보기, 도감 항목 열람 | **아니오** | 알림 없음 |
| 저장 복원/과거 기록 이관/측정·훈련장 | **아니오** | 알림 없음 |

## 5. 추천 시스템 설계 — 확정된 획득에서 딱 한 번

**핵심 원칙: 실제 획득 성공 → 영구 발견 집합의 전후 차이 → 알림 이벤트(다중 ID) → 시각 표시**.

1. **성공한 지급만 감지:** `acquire()`/`claim_fusion()`/`economy.acquire()` 등 실제 성공 결과가 우선. 획득 후보 열람·실패 시도는 제외.
2. **기본 ID로 중복 제거:** 구체 +N 강화는 동일 종류로 판단하고 보유 여부와 무관하게 `discovered_*`를 기준으로 한다.
3. **기존 값과 변경값을 구분:** `profile.discover()`의 현재 bool만으로는 아이템 이름을 특정할 수 없으니, 호출 전후 배열 차이 또는 **새 ID 목록을 반환/이벤트로 발행**하는 경계 설계 권고.
4. **기록 저장:** 영구 프로필 저장 시도 및 실패 처리 정책을 확정한다. 기록되지 않았는데 `영구 도감 기록 완료`라고 단정하는 문구 금지.
5. **알림 등록:** `{kind, base_id, source, run_serial?}` 같은 **임시 UI 이벤트 데이터 모델 제안**. 현행 저장 스키마가 실제로 이 키를 제공하는 것으로 가장하지 않는다.
6. **레이어/큐 처리:** 2~5회 동시 획득·신규 합성·유물 지급 시 알림을 **한 건씩 또는 짧게 묶어** 표시. 동일 ID/동일 영구 발견 중복 큐 등록 방지.
7. **이동/전투 방해 금지:** 토스트는 정보 표시용이며 **마우스 입력을 가로채거나 추가 전투 정지를 만들지 않는다**. 기존 보상 선택으로 이미 멈춘 경우 원래 상태 유지.
8. **도감 선택 노출:** 발견 도감의 목록·카운트는 지금처럼 영구 목록 기준. 추가 `NEW` 상태는 따로 관리.

### 5.1 우선순위 및 기존 시스템 충돌

- `UI-2026-10-30-10`의 **위험 이벤트/보스 등장 UI**보다 신규 발견 토스트 우선순위가 낮다. 보스·정예 경고 중에는 토스트를 대기시키거나 다른 안전 영역으로.
- 기존 전투 HUD의 시계·오브·가방·획득 카드·보스 HP바 가림 금지.
- 보상 수령 영수증(`reward_reveal.receipt`)과 동일한 획득에 대한 알림은 **중복 메시지 두 개를 동시에 띄우지 않도록 결합**하는 안 우선.
- `announce()` 단일 공용 문자열을 신규 발견 큐로 그대로 활용하는 것은 지양. 이벤트 유형·우선순위를 분리한 짧은 UI 레이어 검토.
- 새 BGM을 만들거나 기존에 제거된 임시 BGM을 되살리지 않는다. 효과음도 On/Off 설정을 존중하고, 시청각 접근성을 고려해 소리만으로 구분하지 않는다.
- 도감 `NEW`를 누르는 행동이 전투 중 보상 선택/편집의 일시정지 상태를 바꾸면 안 된다.

## 6. 발견 도감 NEW 상태 — 독립적인 제안

**현재 도감에는 `discovered_*` 배열만 있고, '발견은 했지만 도감에서 아직 확인하지 않은 항목' 별도 상태가 없다.**

추천 개념:
- 기본 주문/완성 합성/유물 각각 발견한 ID 중 **확인하지 않은 ID**에만 `NEW` 작은 배지.
- 도감 탭에 `새로운 발견 N개` 집계.
- 항목 상세를 **실제로 선택/열람했을 때만** 확인 완료 처리. 단순 도감 진입이나 다른 탭으로 이동했다는 이유로 전부 읽음 처리하지 않음.
- 게임을 종료/다시 켜도 유지되는 동작을 원하면 **프로필 스키마/검증/백업/저장 정책 변경**이 선행되어야 한다.
- 기록이 없는 기존 사용자 프로필/버전 이관 때 과거 수십 개를 전부 `NEW`로 다시 띄우는 **소급 알림 폭탄**은 피해야 한다. 기존 발견 항목은 확인 완료로 간주하는 등 마이그레이션 정책을 별도 결정.
- 도감의 발견 여부·미발견 내용 가림 규칙은 그대로 유지. `NEW`는 **이미 발견된 항목에만** 적용하고 미발견 정보를 노출하지 않는다.
- `NEW` 기능이 구현되지 않은 동안 **화면에 도감 새 알림 개수를 가상으로 표시하지 않는다.**

이 제안은 기존 [도감 보고서 UI-2026-10-30-04](2026-10-30-collection-codex-ui-research-proposal.md)와 연결하되, **영구 첫 발견의 저장과 사용자가 실제로 읽었는지 여부는 다른 상태**임을 명시한다.

## 7. 구현 우선순위 — 사용자 별도 승인 이후

| 단계 | 제안 범위 | 확인해야 할 실제 행동 |
|---|---|---|
| P1 | **신규 발견한 정확한 ID 추출**과 기존 단일 bool 개선/어댑터 | 이미 발견한 항목의 재획득은 알림 0회, 신규 1종의 ID 정확성 |
| P2 | **마법/유물 공통 작은 발견 토스트** | 지급 직후 1회 표시, HUD 가리지 않음, 가방/마우스 입력 비차단 |
| P3 | **합성 첫 발견의 특별 효과** | 합성 성공 시점만, 기존 합성·상자 연출에 통합 |
| P4 | **여러 동시 발견의 묶음/큐**와 다른 메시지 우선순위 | 단일 상자 1/3/5개 보상·시작 다중 발견에서도 소실/무한 대기 없음 |
| P5 | **도감 `NEW` 확인 상태 저장** | 해당 항목만 확인 처리·재실행 유지·옛 프로필 호환 |
| P6 | 최종 아이콘·효과음·피드백 폴리시 | Slay the Spire/Magicraft 원작 에셋 복사 없이 카툰 스킨 일치 |

## 8. 테스트 계획 (이번 작업에서 실행하지 않음)

1. 새 프로필 첫 실험 시작 시 **시작 주문 여러 개 최초 발견**: 아이템별 중복 없이 묶거나 순서대로 출력하고 실습 시작 대사를 가리지 않음.
2. 같은 프로필로 새 실험 재시작: 이미 본 시작 주문은 **축하 0회**.
3. 기본 주문 획득, 강화 +1/+2/+3, 같은 기본 주문 재획득을 분리해 처음 발견 판단만 1회.
4. 실제 합성 성공/재료 부족·취소·불법 슬롯 배치/이미 발견한 합성 재완성에서 알림 조건을 분리. **실제 성공하지 않은 합성을 축하하지 않음**.
5. 유물 보상/제작으로 최초 획득, 동일 유물 획득 실패/기존 도감 발견 후 다른 런 획득을 분리.
6. 보상 상자 **1/3/5개 결과**에 여러 새로운 마법/합성이 들어가도 알림의 ID·개수·순서/표시 범위가 정확. 실제 보상 지급 실패/대체 `gold` 처리 시 **지급된 것만** 축하.
7. 보상 선택/상자 공개/작업대/전투 편집/실험 결과/정예·보스 경고 중에 같은 화면 공간을 이중 점유하지 않음.
8. 화면 가장자리, `1280×720`, `1600×900`, `1920×1080` 실제 GUI에서 잘림·시계/오브/보스 HP바 가림·클릭·드래그 방해 없음.
9. ESC 일시정지/Tab 가방/전투 재개·보상 명시 재개 시 토스트의 표시 시간/소실·대기 상태가 기존 게임 상태를 오염시키지 않음.
10. 체크포인트 저장 후 타이틀·재실행·이어하기/예전 기록 `load_profile()` 이관: **과거 발견 축하 재생 없음**.
11. 훈련장·측정 환경·기록 수집이 차단된 특수 실행에서 일반 유저의 영구 발견/팝업을 오염시키지 않음.
12. 프로필 저장 실패·복구 파일·옛 버전 프로필/누락된 `NEW` 상태 처리 및 데이터 보존, **실제 저장 성공과 UI 표현 일치**.
13. `NEW`를 지원한다면 도감에서 선택한 항목만 확인 완료·탭 배지 감소, 아직 안 본 항목은 재시작해도 유지.
14. **소스 열람 / 자동 테스트 / 실제 Godot 화면·입력 / 실전 전투 방해 여부 / 최종 아트 미관**을 별도 증거 수준으로 확인.
15. 발견 알림에 새 데이터 저장이 생기더라도 전투 계산, 드롭, 합성 결과, 마석·체력 보상, 영구 능력치 등에 영향을 주지 않는지 회귀 확인.

## 9. 미확정 결정 및 권장 원칙

1. 시작 마법 여러 개 신규 발견 시 개별 토스트보다 **한 번의 묶음 카드**로 표시할지.
2. 일반/유물 토스트 정확한 노출 시간(예: 제안 1.5~2초)과 위치.
3. 합성 첫 발견의 큰 카드 연출이 보상 화면 안에서만 진행되는지, 제작대 합성에서도 동일하게 진행할지.
4. 알림이 너무 많이 몰릴 때 모든 이름을 읽을 수 있게 큐를 쌓을지, 개수 요약과 나중에 도감 확인을 병행할지.
5. 도감 `NEW`가 **영구 저장되는 읽지 않음 상태**인지, 현재 런 동안만 보이는 표시인지.
6. 프로필 저장에 실패했을 때 `도감에 기록 완료`로 표시할지 말지(권고: 실패를 감춘 성공 메시지 금지).
7. 표시 품질/접근성에 필요한 약한 애니메이션·효과음·플래시 강도는 실제 렌더 후 비교. 사용자 승인 전 확정 아님.

## 10. 이번 작업 범위 및 후속 연결

**실제 수행:** 바로 앞 HUD2 대화의 Dead Cells/Magicraft/Vampire Survivors/Slay the Spire/Balatro/HoloCure 발견 UI 비교 정리, GitHub의 영구 발견 자료 구조·획득/합성/유물 지급·영수증·도감 코드 재점검, 본 문서 등록 및 공용 INDEX 연결.

**수행하지 않음:** GitHub 제품 코드 수정, 저장 스키마 추가, 발견 팝업/도감 NEW UI 구현, Godot 엔진 실행·키보드/마우스/화면 검증, 최신 참고작 직접 실행, 상용 원작 에셋 반입, 새 BGM·SFX 생성.

**정리:** 신규 발견은 `획득`과 같은 것이 아니라 **프로필에 처음 기록되는 영구 종류**다. 일반 아이템은 작게, 새로운 합성은 특별하게, 도감에는 나중에 확인할 수 있는 상태를 **별도 기능으로 제안**한다. 상태 **PROPOSED**는 사용자 코드 구현 승인이 아니다.
