## 1. 이 화면의 목적

현재의 `실험 기록`은 단순 승패 확인뿐 아니라 **한 판에서 어떤 마법 조합으로 어디까지 갔는지 기억하고, 다음 실험을 개선하는 화면**이 되어야 한다.

플레이어의 주요 질문:
1. 최근 어떤 실험을 했고 수습에 성공했는가?
2. 특정 실험의 시작 조합·전투 시간·처치 수·획득 마석은?
3. 그때 오브 1~4에 **어떤 마법을 어떤 순서와 강화 단계**로 넣었는가?
4. 어떤 유물을 사용했고 어느 웨이브까지 도달했는가?
5. 지난 실험의 결과·조합을 비교하려면 얼마나 적은 조작이 필요한가?

**우선 권고:** 기본은 **왼쪽 최근 실험 목록 + 오른쪽 선택 실험 상세**, 서적/실험 일지 분위기는 시각적 스타일로만 보강.

### 2.1 화면에 이미 표시되는 항목

`RunUI.records()`는 `Rect2(160,100,1120,700)`의 모달과 `1000×390` 스크롤 컨테이너 안에서 기록을 **문자열 한 줄씩** 출력한다.

- 화면 상단: `수습 N회 · 실패 N회 · 루미의 멈춤 조건 단서 발견 여부`
- 각 기록: `수습/실패 · 시작 키트 이름 · 전투 시간 · 처치 수`
- 기록이 없을 때: `첫 실험의 결과를 기다리고 있어요.`
- 하단: `돌아가기` → 타이틀.
- 현재 목록의 각 행은 **선택 가능한 상세 버튼/카드가 아니라 `Label`**이다.

**핵심 구조 문제:** 이미 저장한 자세한 정보를 보려면 해당 행을 눌러야 하는데, 현재는 **행 선택/선택한 런 상세 패널이 없다**.

### 2.2 실제로 저장하는 필드

| 구분 | 실제 저장/보유 상태 | 현 실험 기록 화면에 표시? |
|---|---|---|
| 수습·실패 누적 | `profile.data.wins/losses` | 상단에 표시 |
| 다음 실험에 남는 단서 여부 | `profile.data.lumi_clue` | 상단에 표시 |
| 최근 종료된 런 | `profile.data.records` **최근 최대 10건**, 최신 순서로 앞에 추가 | 목록 표시 |
| 승패/시작 조합 | `won`, `character`, `kit` | 승패·키트만 표시 |
| 전투/제작 시간 | `combat`, `preparation` | 전투 시간만 표시 |
| 처치/마석 | `kills`, `earned` | 처치만 표시 |
| 도달 웨이브/종료 이유 | `wave`, `reason` | 미표시 |
| 최종 오브 배열 | `recipes` (오브별 마법 ID 배열. 강화된 부품 ID도 포함 가능) | 미표시 |
| 유물 | `relics` (획득한 유물 ID 배열) | 미표시 |
| 웨이브 완료 내역 | `waves` (각 완료 웨이브 사본) | 미표시 |
| 런 중복 식별 | `run_id` 및 최근 `completed_ids` | UI 미표시(내부 관리) |
| 최고 전투 시간 | `best_combat` (승리한 런의 짧은 기록) | 미표시 |

### 2.3 주의: 실제 데이터가 없는 항목

- **플레이 날짜/시각(종료 타임스탬프):** 런 기록 `end_run()`에 해당 필드를 기록하지 않음. 화면에 가상의 날짜를 만들지 않는다. 최근 순서 또는 `최근 기록`으로 표시.
- **오브 자체의 성장 랭크 `orb_growth[].rank`:** 결과 화면에는 현재 게임 상태로 표시하지만, 영구 `run_record`에는 별도 오브 랭크 필드 없음. 마법 구체의 `+N` 정보와 **오브 성장 랭크는 서로 다르다.**
- **마법별/오브별 피해량·DPS:** 런 이력 저장 필드 없음. 기존 데이터에서 추정해 표시하지 않는다.
- **최근 10판을 초과한 과거의 개별 기록:** `records`는 오래된 기록을 잘라내므로 목록/상세에 재현할 수 없다. 다만 `wins/losses` 누적치는 보존된다.
- **웨이브별 마지막 미완료 구간 스냅샷:** `wave_records.append()`는 **웨이브 완료 처리 때** 실행된다. 패배한 웨이브의 완료 기록은 없는 경우가 일반적이며 마지막 `wave`만 런 전체 필드로 알 수 있다.
- **웨이브별 `earned`:** 해당 웨이브에서만 얻은 마석이 아니라 **그 시점까지의 누적 `economy.total_earned`**을 기록한다. `웨이브 획득 마석`으로 표기하면 잘못된다.
- `waves`의 사본은 각 완료 웨이브의 `wave`/`seconds`/`kills`/`earned`/`recipes`를 담는다. **당시 유물 현황이나 모든 성장 상태**가 별도 저장된 것은 아니다.

이는 **정보 위계 개념도**이지 최종 픽셀·색·에셋을 확정한 UI가 아니다.

### 4.1 헤더: 누적과 최근 기록을 정확히 구분

- `수습 N회 / 실패 N회`는 전체 누적 기록 기준.
- `최근 기록 10판`은 **보존된 개별 기록 건수**이므로 전체 누적과 일치하지 않을 수 있다.
- 스토리 단서 `lumi_clue`는 실제 해금된 상태일 때만 표시.
- `best_combat`을 쓰는 경우 '최단 수습 전투 시간'처럼 실제 뜻에 맞는 라벨을 쓰고, 기록이 없으면 대시 등 빈 상태.

### 4.2 왼쪽: 최근 기록 목록

- 최근순(현행 `push_front` 순서), **전체/수습/실패** 단일 필터.
- 항목은 `기록 선택 버튼/카드`로 구성. **승패 / 시작 조합 / 전투 시간 또는 도달 웨이브**만 빠르게 노출.
- 행 클릭 시 오른쪽 상세만 교체. 필터/선택/스크롤 위치를 안정적으로 보존.
- 날짜가 기록되지 않은 기존 데이터에 `2026-10-30` 같은 **가짜 날짜**를 추가하지 않는다.
- 실험 번호는 **현재 보존 목록에서의 상대적 위치**로만 사용하고, 실제 게임 전체에서 변하지 않는 고유 ID인 것처럼 표현하지 않는다.
- 항목을 탭/키보드·방향키/엔터로 선택 가능하도록.
- 목록이 없을 경우: `첫 실험의 결과를 기다리고 있어요.`와 타이틀 복귀 안내. 수습 필터 결과가 비면 `수습 기록이 없어요.` 등 빈 결과 표시.

### 4.3 오른쪽: 선택한 실험의 상세

**가장 먼저:** 승패 뱃지/시작 키트/도달 웨이브/종료 원인.

**핵심 통계:** 전투·제작 시간, 처치 수, `이번 판 획득 마석`. 총 획득 마석은 **영구 보상으로 오인하지 않도록** 명시.

**오브:** 오브 1~최대 4개의 실제 `recipes` 순서/각 칸 아이콘, 부품별 강화 `+N` 표시/툴팁. **오브 자체 성장 단계는 역사 데이터에 없으므로 미표시**, 별도 승인 후 저장 필드를 추가할지 결정.

**유물:** `relics`에서 실제 보유한 ID를 아이콘으로 보여주고 이름/기능 툴팁 제공. 저장값에 없는 유물·미발견 아이템을 임의 생성하지 않는다.

**설명:** 게임 종료 이유 `reason`과 실제 저장된 데이터만 보인다. 결과 화면의 즉석 캐릭터 대사 전체를 과거 기록에 자동 보존했다고 오인하면 안 된다.

**연결:** 기존 [승리·패배 결과 UI](2026-10-30-victory-defeat-results-ui-research-proposal.md)의 슬롯/유물 카드 디자인과 같은 컴포넌트를 재사용하는 것이 최우선이다. 그러나 결과 화면은 현재 런 메모리를 사용하고, **실험 일지는 영구 저장된 런 스냅샷만으로 재구성**해야 한다.

### 4.4 펼침 영역: 완료 웨이브별 실험 과정

`waves` 배열을 누르면 **완료한 웨이브만** 실제 기록에서 표시.

- 각 스냅샷: `wave`, `seconds`, `kills`, `earned`, `recipes`.
- `seconds`는 해당 완료 웨이브의 시간, `kills`는 해당 웨이브 처치 기록.
- `earned`는 **완료 시점까지 누적된 총 획득 마석**이라고 명시. 개별 웨이브 마석으로 계산해 보여주려면 이전 누적과의 차이를 **추가 계산**한다는 사실을 명시하고, 첫 구간·미완료 구간/과거 버전 기록 처리를 검증해야 한다.
- 패배한 웨이브는 현재 `waves` 배열에 완료 스냅샷이 없는 상태가 가능하므로 `미완료 · 상세 기록 없음`처럼 표현. 완료로 위장하거나 웨이브별 오브 배열을 생성하지 않는다.
- 처음에는 **간단한 연표/접이식 내역**만 제안. 상세 그래프·마법 DPS·플레이어 위치/HP 변화 곡선은 저장되지 않은 데이터가 필요하므로 제외.

## 6. 디자인 원칙

- **Hades의 보안 로그/일지 분위기**를 마녀 실습장 톤으로 변환: 가벼운 크림·라벤더·둥근 패널. 현실적인 가죽책/나무/금속 질감 과용 금지.
- **Slay the Spire처럼 실물 빌드가 내용의 중심**이 되어야 한다. 캐릭터 초상/장식이 마법 슬롯을 압도하지 않는다.
- **외부 분석 앱처럼 통계 대시보드화하지 않는다.** 최근 10건이면 리스트·필터·선택 상세 정도로 충분.
- **일반 승패 결과 화면과 '같은 룩'이되 다른 작업:** 결과 화면은 직후 감정 연출/재도전, 실험 기록은 장기 복기·비교.
- 발견 도감과도 아이콘/툴팁 규칙을 공유하지만, 도감처럼 미발견 항목까지 열람하는 UI로 만들지 않는다. 기록에는 **그 판에서 실제 사용한 아이템만** 노출.
- **비주얼은 수치를 가리지 않는다.** 날짜·DPS·랭크 등 없는 정보를 플레이어의 성취 보상처럼 꾸며내지 않는다.

## 7. 승인 후 작업 순서/검증 (이번에는 미실시)

| 단계 | 변경 제안 | 완료 확인 방법 |
|---|---|---|
| P1 | `records()`의 텍스트 Label → 선택 카드/필터/상세 | 최근 10건 승패 필터·선택 유지·실제 필드 정확히 표시 |
| P2 | 기존 오브 슬롯·유물 정의를 저장 스냅샷 렌더링에 재사용 | 오브 최대 4개, 구체 단계·종류·빈칸·유물 정보 일치 |
| P3 | 완료 웨이브별 접이식 진행 기록 | 스냅샷 누락·이전 버전의 `waves` 없음·누적 마석 정확성 |
| P4 | 카드/책갈피 스타일과 결과 화면 공통 디자인 마감 | 실제 화면/해상도/텍스트 판독·선택 상태 검증 |
| 별도 결정 | 플레이 날짜·오브 자체 성장 랭크 저장, 피해/DPS 계측 | 저장 스키마·이전 기록 마이그레이션·회귀 검사 선행 |

### 7.1 구체적 Godot 검증 체크리스트
1. 기록 0/1/10건, 수습만/실패만, 필터 결과 0건을 실제 화면에서 확인.
2. `records` 최신순·누적 `wins/losses`가 서로 다른 범위임을 표시하고, 10건 상한을 변경하지 않음.
3. 한 판 상세의 승패·키트·이유·전투/제작 시간·처치·마석·웨이브가 실제 JSON과 일치.
4. 오브 1~4 / 슬롯 수 변동 / `+3` 이하 강화 구체 / 빈칸 / 합성 마법 아이콘을 정확히 보여줌.
5. 기록 속 유물 ID가 실제 게임 정의로 매핑되며, 정의가 없거나 옛 ID여도 UI 충돌 없이 처리.
6. `waves` 없음/빈 배열, 이전 버전 저장 필드 누락, 마지막 실패 웨이브 미완료 기록을 안전하게 처리.
7. `waves[].earned`를 해당 웨이브의 독립 마석처럼 표시하지 않음.
8. 목록 스크롤·필터·키보드/마우스 포커스·도감/타이틀 복귀, `Esc` 이동을 실제 입력으로 확인.
9. `1280×720`, `1600×900`, `1920×1080` 렌더에서 오브 배열·툴팁·카드가 겹치지 않음.
10. 기록 UI 조회만으로 프로필·발견 도감·실험 결과가 변하거나 `run_id`가 다시 기록되지 않음.
11. 기록 재구성에 쓰는 공통 컴포넌트가 직후 승패 결과 UI와 혼동하여 **새 게임 시작/보상 지급 버튼을 노출하지 않음**.
12. **정적 코드 열람 / 자동 검사 / Godot 실렌더·실입력 / 사용자 미관·사용성 평가**를 분리 기록.

## 8. 미결정 및 제한

- 실험 일지를 전면 페이지처럼 넓힐지, 기존 `1120×700` 모달 안에서 충분한지 실제 조합 슬롯 밀도로 비교 필요.
- 목록의 결말/원인 노출량, 웨이브 연표를 기본 접음/펼침 중 무엇으로 둘지.
- 최근 10건 상한을 유지할지, 플레이 날짜·오브 성장 랭크 기록을 새로 시작할지는 **이번 UI 자료 조사에서 확정하지 않음**.
- 기존 스토리·다른 마녀/진엔딩 기록은 후속 구현 상태에 맞춰 따로 연계.
- 로그 조회에서 실제로 없는 데이터나 옛 저장 데이터의 필드를 임의 채우지 않는다.
- 아이콘·이펙트·음악·원작 아트는 새로 수입/생성하지 않음.

- HUD2의 Slay the Spire/Hades/Monster Train/Scry/Spire Vault UI 비교를 **자료 근거별로 구분해 설계안**으로 정리.
- 공식 Run History 공지와 실제 분석 도구 사이트 공개 설명 확인.
