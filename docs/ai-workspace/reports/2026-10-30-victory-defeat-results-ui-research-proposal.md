## 1. 목적과 평가 기준

- **승리:** 보스를 쓰러뜨린 성취감을 순간적으로 보여주고, 성공한 실험과 빌드를 기록한다.
- **패배:** 무조건 비극적이거나 처벌처럼 보이기보다 실패한 마법 실험의 코믹함을 살리고, **어디까지 갔으며 어떤 마법을 썼는지** 확인하게 한다.
- **공통:** 이번 판 기록을 읽고 즉시 같은 조합으로 다시 하거나 다른 조합을 선택하도록 한다. 결말 대사와 데이터 통계를 보기 위해 **두 개의 필수 페이지를 거치게 하지 않는다.**
- 목표는 데이터를 더 많이 넣는 것만이 아니라 **결과 문구 → 캐릭터 반응 → 빌드/기록 → 재도전 행동**이라는 시각적 위계를 명확히 만드는 것이다.

## 2. 실제 현재 구현 — 이번 정적 코드에서 확인

주요 근거: [`front_flow.gd`](../../../scripts/front_flow.gd)의 `results()`, [`run_ui.gd`](../../../scripts/run_ui.gd)의 `ending()/results()`, [`game.gd`](../../../scripts/game.gd)의 `end_run()`, [`player_profile.gd`](../../../scripts/player_profile.gd), [`FRONT-FLOW-v1.md`](../../FRONT-FLOW-v1.md).

| 구성 요소 | 현재 구현 확인 |
|---|---|
| 결과 화면 | `RunUI.ending()`/ `results()`는 모두 `FrontFlow.results()`를 호출. **결말과 결과가 같은 화면**에 있다 |
| 승패 제목 | 승리 시 `사고 수습 완료`(민트), 패배 시 `실험 중단`(핑크) |
| 왼쪽 | **동일한 루미 초상**, 결과에 따른 보조 문구, 런 자원 소멸·기록 보존 안내 |
| 오른쪽 상단 | 성공/실패별 **짧은 결말 대사** 블록 |
| 핵심 기록 | **전투 시간(`elapsed`) / 제작·편집 시간(`prep_elapsed`) / 처치 수(`kills`) / 이번 판 총 획득 마석(`economy.total_earned`)** |
| 빌드 | 실제 `orb_recipes`에 따른 **오브 1~4의 슬롯 순서·오브 성장 랭크**를 표시하고, 유물은 이름들을 나열 |
| 다시 하기 | `같은 시작 조합으로 다시`, `다른 시작 조합 고르기`, `타이틀` |
| 같은 조합 재시작 | `g.state=="ended"`일 때 `begin_lumi_run(g.selected_kit,false)`를 호출해 이전 시작 조합으로 도입을 생략하고 시작 |
| 기록 저장 | 종료 시 `run_record`에 승패·캐릭터·키트·전투/준비시간·처치·마석·웨이브·이유·오브 레시피·유물·웨이브별 기록 저장, 중복 종료 방지 |
| 패배 원인 | `end_reason` 문자 정보가 존재. 화면에는 승패에 따라 문구가 달라짐 |
| 승리 표기 | 현재 코드에 **일반 결말**·**멈춤 조건의 단서 발견** 문구가 있음. 스토리의 진엔딩/개편과의 연계는 별도 작업 |
| 오디오 | `end_run()`이 결과 진입 뒤 승리에는 `reward`, 패배에는 `hurt` 사운드 호출 |
| 영구 기록 | 프로필에는 누적 수습/실패와 발견 기록이 남으며, 다음 판의 전투 자원·장비를 영구 유지하는 구조는 아님 |

### 확인된 구조적 한계와 검증해야 할 가설

1. **승패 차이가 문구·색·짧은 대사에 집중**되어 있어 결과 화면의 감정적 인상이 비슷할 가능성. 실제 캐릭터 표정이나 전용 승패 연출의 차이는 현재 `results()` 코드에서 확인되지 않는다.
2. 오른쪽의 **통계/오브/결말**이 비슷한 패널 밀도로 놓여서 성공 순간의 메시지가 상대적으로 약할 수 있다. **실제 미관 만족도는 사용자 평가 및 Godot 렌더로 판단**해야 한다.
3. 유물은 **이름 나열**로 표시되며 선택한 유물의 시각적 실루엣이 약할 수 있다.
4. `run_record`에 **웨이브(`wave`)**는 존재하지만 `results()`의 상단 대표 통계에는 현재 표시하지 않는다.
5. 결과창의 **오브별 피해량, DPS, 각 마법 기여도**는 현재 `run_record`에 수집·제공되지 않는 것으로 확인. 이를 넣으려면 UI 수정만으로는 불충분하며 실제 전투 계측 설계·검증이 필요하다.
6. **'전투 종료 전장 이미지 유지'는 확인된 현재 기능이 아니다.** `end_run()`에서 적/탄환/마법을 먼저 정리하므로 결과 연출 전에 최종 전장 모습을 남기려면 별도 캡처/연출 계층 설계가 필요하다. 현재 코드가 프리즈된 마지막 전장을 그대로 남긴다고 단정하지 않는다.

## 3. 이전 대화에서 조사한 레퍼런스 7종

다음 비교는 **이전 HUD2 대화에서 수집·검토한 결과 UI 자료**를 기록한 것이다. 이번 GitHub 보고서 업로드 시 해당 게임의 최신 버전·이미지를 **다시 실행·측정·검증하지 않았다**. 외부 이미지, 원본 레이아웃 파일, 음향을 저장소에 반입하지 않는다.

| 게임 | 승패/결과 UI에서 참고한 특징 | 우리 게임에 적용할 부분 | 한계 |
|---|---|---|---|
| **HoloCure** | `STAGE COMPLETE!` 같은 큰 결과 표시, 배경을 이어받는 간단한 보상/재도전 | **승패 확정 순간의 큰 문구와 빠른 진행** | 빌드/오브 1~4의 상세를 이 크기로 전부 담기 어려움 |

| **Soulstone Survivors** | 패배에서도 스킬·전투 기록의 상세를 유지 | **실패한 빌드도 비교 자료로 존중** | 본 게임에는 지나치게 많은 통계가 첫 화면을 복잡하게 만들 수 있음 |
| **Hades** | 승리를 기념하는 커다란 `VICTORY` 시각 프레임과 클리어 정보 | **성취감과 결과 화면의 장면성** | 원작의 UI 장식·아트/문구·음향 그대로 재사용 금지 |
| **Brotato의 승패 대응 비교** | 서로 다른 결과 제목에도 유사한 빌드/아이템 배치 | 승리/패배의 데이터 규칙은 동일하게, **분위기만 차등 연출** | 동일 화면 구조여도 실패 이유와 다음 행동은 차별화 필요 |

### 레퍼런스 우선순위

1. **Brotato:** 결과 화면의 **구조/무기·아이템(우리의 오브·유물) 기록**.
2. **HoloCure:** 간단한 **종료 순간의 승패 타이틀과 빠른 재도전 동선**.
3. **Hades:** **승리할 때 특별한 기념 장면**이라는 감정적 연출.
4. **Vampire Survivors / DRG: Survivor:** 추후 상세 전투 통계 계측·표시가 생길 때 참고.

참고 게임의 UI는 방향만 참고한다. 각각의 실제 게임 진행/보상/결말 구조를 우리 게임 규칙으로 단정해서 이식하지 않는다.

## 4. 가장 추천하는 구성

**결론: `Brotato식 빌드 기록 + HoloCure식 즉각적인 결과 선언 + Hades식 승리 강조`.**

**승리와 패배는 동일한 기본 레이아웃**을 사용하되, 제목·표정·배경의 명도/색·연출·짧은 문구로 서로 다르게 체감하게 한다.

### 4.1 공통 정보 위계

1. **최상단:** `사고 수습 완료!` 또는 `실험 중단!`. 시각적으로 가장 크게.
2. **큰 캐릭터 영역:** 루미의 반응을 보여주는 일러스트/표정(별도 제작이 필요한 경우 승인 후).
3. **간결한 결과 통계:** 시간/처치/이번 런 획득 마석, 패배 시 도달 웨이브를 우선 제안.
4. **이번 실험의 빌드:** 오브 1~4 슬롯 순서와 성장 단계, 유물 아이콘·툴팁(현재는 유물 이름).
5. **짧은 결말과 영구 단서:** 현재 스토리 정책과 일치하는 문구. 본문 분량을 축소하되 **결말은 결과 화면 안에 유지**.
6. **하단 CTA:** `같은 시작 조합으로 다시`(1차), `다른 시작 조합 고르기`(2차), `타이틀`(보조).

### 4.2 가로 16:9 레이아웃 개념도

```text
┌──────────────────── [사고 수습 완료! / 실험 중단!] ──────────────────┐
│ (좌) 캐릭터 반응 일러스트   (우상) 이번 런의 핵심 통계 3~4개           │
│      루미의 짧은 반응       [시간] [처치] [획득 마석] [도달 웨이브]    │
│                            ┌────────────────────────────────────┐ │
│                            │ 오브1 [칸][칸][...] · 성장 +N      │ │
│                            │ 오브2 [칸][칸][...] · 성장 +N      │ │
│                            │ 오브3 [칸][칸][...] · 성장 +N      │ │
│                            │ 오브4 [칸][칸][...] · 성장 +N      │ │
│                            └────────────────────────────────────┘ │
│      짧은 결말 / 단서      [이번 유물: 실제 획득 아이콘·툴팁]         │
│                            [같은 시작 조합으로 다시 (강조)]          │
│                            [다른 시작 조합]          [타이틀]       │
└───────────────────────────────────────────────────────────────────┘
```

- 위는 **요소 간의 상대적 위계**를 설명하는 텍스트 도식. 픽셀, 실제 화면 스크린샷, 확정된 일러스트/컬러가 아니다.
- 오브 4개 및 슬롯 6~8칸의 **최대 구성에서도 가독성을 유지**해야 한다. 현재 `results()`는 오브당 `375×115` 패널에 최대 2열 배치.
- 결과 화면을 매우 크게 재설계하더라도 **캐릭터/통계/빌드/재도전이 화면 한 장에서 모두 식별**되도록 한다.

## 5. 승리·패배의 감정 연출 분리

| 연출 요소 | 승리(제안) | 패배(제안) |
|---|---|---|
| 첫 메시지 | `사고 수습 완료!` 크게 | `실험 중단!` 크게 |
| 루미 | 기뻐함/당당함/안도함 | 그을림/당황함/아쉬움 |
| 분위기 | 밝은 크림·라벤더, 짧은 반짝임 | 다소 낮은 채도, 연기/작은 잔재 |
| 강조 정보 | 성공과 실제 획득한 단서 | 실제 패배 원인·도달 웨이브 |
| 공통 빌드 | 사용한 오브/유물 전체 표시 | **실패한 오브/유물도 같은 정보량으로 표시** |
| 주요 행동 | 같은 시작 조합으로 다시 | 같은 시작 조합으로 재도전 |

- 패배를 무거운 비극으로 처리하는 것보다 **'마법 사고'가 벌어진 코믹한 실패**의 톤에 맞춘다.
- 승리 성취감을 위한 별도 연출과 실제 일반·진엔딩의 스토리 구조는 **구분**한다. 진엔딩 대사를 이 문서가 대신 확정하지 않는다.
- 단서가 **실제로 발급되는 상황에서만** 획득/발견처럼 표시한다. 매번 보상인 것처럼 과장하면 안 된다.
- 새 승리/패배 전용 캐릭터 표정, 배경·음향·VFX가 필요하다면 **별도 아트 범위 승인** 후 진행. 기존 아트로 확인 가능한 중간 버전을 우선 검토해도 된다.

## 6. 결과 화면 정보: 유지/개선/미구현 분리

| 정보/기능 | 현재 상태 | 제안 |
|---|---|---|
| 전투 시간 | **표시 중** | 유지 |
| 제작·편집 시간 | **표시 중** | 유지; 가장 중요한 3~4개 중 어디에 둘지 UI 시험 |
| 처치 수 | **표시 중** | 유지 |
| 이번 판 획득 마석 | **표시 중** | 유지하되 **다음 판으로 이월되는 보상으로 오인하지 않게** 표시 |
| 도달 웨이브 | `run_record.wave`로 기록됨; 현재 주요 카드에는 없음 | **패배 화면 우선**으로 대표 통계 표시 검토 |
| 오브 1~4 조합/성장 | **표시 중** | 더 읽기 쉬운 슬롯/번호/강화 프레임으로 정리 |
| 유물 | **현재 이름 나열** | 실제 보유 유물의 아이콘형 리스트·툴팁 권고 |
| 결과 원인·짧은 결말 | **표시 중** | 위계만 수정하고 통합 유지 |
| 같은 조합/다른 조합/타이틀 | **모두 기능 연결됨** | 가장 중요 동작을 크게, 보조 버튼을 분리 |
| 오브별 피해량/DPS | **결과 저장 필드에서 미확인** | 이번 UI만으로 추가 불가; 별도 계측 설계가 먼저 |
| 누적 최고 기록/개인 베스트 | 프로필에 일부 영구 기록이 있으나 결과 화면 연동은 미확인 | 실제 기록 정의/저장 완료 상태 확인 후 별도 검토 |
| 승리/패배 전용 인물 그림 | `results()`에서 동일 `portrait()` 사용 | 각 반응 차별화 **제안 단계** |

## 7. 유지해야 할 흐름·계약

- `end_run(won)`은 **동일 런 중복 종료를 막으며** 전투 요소를 정리하고 런 기록을 저장한다. UI 개편만으로 종료 순서를 변경하지 않는다.
- **결말과 결과는 한 화면**: 새 필수 승리 컷신 페이지·통계 페이지를 불필요하게 삽입하지 않음. 연출 오버레이가 있다면 스킵/즉시 결과 열기 가능하도록 검토.
- **재도전 경로:** `같은 시작 조합으로 다시`는 기존 `selected_kit`로 새 판을 시작하고 도입을 건너뜀. `다른 시작 조합 고르기`는 준비 선택 단계로 이동. `타이틀`은 정상 복귀.
- 저장: 종료 결과와 도감 발견 상태만 영구 기록하는 **현행 계약을 유지**. 마석·구체·유물을 결과 화면에서 잘못 영구 보상으로 표현하지 않는다.
- 키보드 `Tab`/화살표/`Enter`/`Esc` 및 마우스의 기존 결과 화면 포커스·복귀 정책 보존.
- `run_record` 값이 가상 피그마/목업의 예시 수치와 일치하지 않아도 실제 런 값을 우선한다.
- 새 전투 통계(DPS 등)를 만들 경우에는 **최소한 피해 귀속 규칙·다단 히트·복제/연결 마법·보조 기여도**의 명세와 검증이 선행되어야 한다.

## 8. 구현이 승인될 경우 제안 순서

| 단계 | 작업 | 작업·기능 경계 |
|---|---|---|
| P1 | 상단 승패 제목·캐릭터·결말 위계 개선 | 현 `front_flow.gd` 결과 UI 레이아웃 중심 |
| P2 | 핵심 통계와 도달 웨이브·빌드 정돈 | 실제 `run_record` 및 현재 런 데이터만 사용 |
| P3 | 유물 아이콘/툴팁 및 오브 1~4의 최대 공간 정리 | 기존 슬롯·유물 표시 유틸 재사용 |
| P4 | 승패별 짧은 반응·효과/사운드 연출 | 새 아트 자산 승인 후, 성능과 입력 고려 |
| P5 | 실제 Godot 런타임/입력·재도전·기록 저장 회귀 시험 | 자동검사와 실제 렌더·미술 만족도를 분리 기록 |

### 사용자 승인 이후 검증 체크리스트 (이번에는 미실시)
1. 실제 승리/패배 `end_run()`에서 서로 다른 제목·색·서사 문구를 표시하며, 판정 데이터가 뒤바뀌지 않는다.
2. 런 기록의 전투/준비 시간·처치·마석·웨이브 및 오브/유물 표시가 **실제 종료 값**과 정확히 일치한다.
3. 오브 최대 4개, 슬롯 6~8개, 유물 최대치 및 긴 결말/이유에서 **텍스트·버튼·아이콘 잘림/겹침이 없다**.
4. `1280×720`, `1600×900`, `1920×1080`의 레이아웃을 실제 렌더로 확인하고 클릭/키보드/필요 시 패드를 검증한다.
5. 승리/패배 모두에서 `같은 시작 조합 재도전`, `다른 시작 조합`, `타이틀` 버튼이 중복 실행되지 않고 정상 동작.
6. 도입 생략, 런 종료 시 몬스터/마법 정리, 카메라·입력 포커스 복귀, 결과 재진입이 기존과 같음.
7. 기록 저장 실패/프로필 경고를 UI에서 숨기거나 성공으로 오인하게 하지 않는다.
8. 멀티 웨이브·보스 처치·중간 사망 경로 모두 결과 화면을 보여주며 게임/카메라가 의도치 않게 계속 진행하지 않는다.
9. 결과 화면의 시각적 기분, 성공 보상감, 패배 후 재도전 욕구는 **사용자 직접 확인 결과**로 남긴다.
10. **소스 확인 / 자동검사 / Godot 실렌더·실입력 / 사용자 미관 승인**을 각각 별개의 검증 수준으로 표시한다.

## 9. 미확정 결정 사항

- 승패별 루미 표정을 실제로 제작할지, 기존 초상/이펙트만으로 시작할지.
- 보스 처치 직후 **전장 일시 정지 오버레이**를 넣을지. 현재 전투 정리 순서상 별도 설계가 필요.
- 결과 화면을 가로형 패널로 유지하면서 위계만 고칠지, 전면 화면/배경 연출까지 개편할지.
- 승리 시의 일반/진엔딩 스토리와 결과 문구를 언제 분리할지.
- 도달 웨이브 등 대표 통계 우선순위 및 장기적으로 오브별 피해 통계를 수집할지.
- 새 VFX·BGM·효과음을 어디까지 도입할지.

**모두 `PROPOSED`. 기존 스토리 확정 정책·프로필·경제/전투를 변경하는 승인은 아니다.**
